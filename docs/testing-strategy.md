# Testing strategy — a deep, point-by-point plan

This is the reference map for the whole project: how to test every kind of thing a Spring Boot
application is made of. Read it once end-to-end now; come back to a single numbered section when
you're about to build that piece. Each section says *what* the technique is, *which tools* it
uses, and *what specifically to cover* — not finished code, since the point is to write it
yourself as you go.

Sources checked while writing this (Spring Boot 4 / Spring Framework 7 are recent enough that
specifics were worth verifying rather than assumed):
- [What's New for Testing in Spring Boot 4 and Spring Framework 7](https://rieckpil.de/whats-new-for-testing-in-spring-boot-4-0-and-spring-framework-7/)
- [Spring Boot reference docs — Testcontainers](https://docs.spring.io/spring-boot/reference/testing/testcontainers.html)
- [Testcontainers + Spring Boot 4 integration test setup](https://www.javacodegeeks.com/2026/08/testcontainers-spring-boot-4-the-integration-test-setup-teams-actually-use.html)

## 1. The pyramid, Spring-Boot-flavored

| Layer | Spring Boot mechanism | Spring context? | Speed | What it proves |
|---|---|---|---|---|
| Unit | plain JUnit 5 + Mockito | none | fastest | a single class's logic/branches |
| Slice | `@WebMvcTest`, `@DataJpaTest`, `@JsonTest`, `@RestClientTest` | partial (just that slice) | fast | one layer wired correctly, everything around it mocked |
| Integration | `@SpringBootTest` (+ Testcontainers) | full | slow | real wiring across layers, real infra (DB/broker) |
| End-to-end | app running as a black box, hit over HTTP | full, out-of-process | slowest | the whole thing actually works for a user |

Most tests should be unit tests. Fewer should be slice tests. Fewer still should be full
integration tests. Keep e2e to a handful of smoke scenarios. The shape matters because it's what
keeps the feedback loop fast — a broken unit test should fail in milliseconds, not after a 30
second Spring context + container startup.

Every test class is named after its tier — `XxxUnitTest` / `XxxSliceTest` / `XxxIntegrationTest` /
`XxxE2eTest` — never a bare `XxxTest`, so the tier is obvious from the file name alone (see
AGENTS.md). E.g. the repository tests in §3 live in `OrderRepositorySliceTest`.

## 2. Unit testing services / domain logic

No Spring context at all — that's what makes these fast and precise.

- **Tools**: JUnit 5 (`@ExtendWith(MockitoExtension.class)`), Mockito for collaborators, AssertJ
  for fluent assertions.
- Constructor injection (not field injection) is what makes this trivial — you can `new` the class
  under test directly with mocked dependencies, no container needed.
- Cover: the happy path, every conditional branch, boundary values (0, 1, max, empty collection,
  null where allowed), and every exception path (what does the service do when a collaborator
  throws?).
- Assert on **behavior/contracts** (return values, thrown exceptions, arguments passed to
  collaborators when that's the actual contract) — not on incidental implementation details. Don't
  `verify()` every single call; only verify interactions that matter to correctness.

## 3. Repository testing

- **Tools**: `@DataJpaTest` + Testcontainers Postgres via `@ServiceConnection` (real database).
- H2 in-memory is tempting but its SQL dialect diverges from Postgres enough to hide real bugs
  (native queries, constraint behavior, date/time handling). Prefer Testcontainers for production
  parity — this project's whole point is learning to do it right.
- **Why not a plain unit test here?** A Spring Data repository *interface* has no logic of its
  own — every query is generated by Spring Data/Hibernate from the method name or `@Query`. A
  mock would only prove Mockito works, not that the query, the constraint, or the cascade rule
  is correct. This tier's whole point is exercising the real thing, which is why it's a slice
  test against a real database rather than a unit test — see §1's table. (A repository *does*
  become unit-testable once it has hand-written logic on top — e.g. a custom implementation
  method with branching — but a plain derived/`@Query` interface doesn't.)
- Cover: custom `@Query` methods (JPQL and native), pagination/sorting (including the empty-result
  case), cascade persist and orphan-removal *and* cascade-delete-of-the-parent (different
  mechanisms — don't assume one implies the other), unique- and not-null-constraint violations
  (assert the right exception surfaces), blank/absent lookup keys, `@Transactional` rollback
  semantics inside the test itself, and round-trip fidelity for values that can silently lose
  precision crossing the JDBC boundary (`Instant` → Postgres `timestamp` is microsecond-precision,
  not nanosecond; `BigDecimal` equality is scale-sensitive, so know whether you mean
  `.equals()` or `.isEqualByComparingTo()` before trusting a money assertion).

## 4. Controller / web-layer testing

- **Tools**: `@WebMvcTest` sliced per controller, service layer mocked with `@MockitoBean`,
  `RestTestClient` (Spring Boot 4's unified fluent client — works against `MockMvc` here, and
  against a live server in section 5, same API) instead of raw `MockMvc`.
- Cover: request/response JSON shape, validation error responses (400 + the exact body shape your
  `@ControllerAdvice` produces), content negotiation, status code per scenario, path/query param
  binding and type conversion edge cases.
- **Spring Boot 4 setup**: `@WebMvcTest` moved out of `spring-boot-starter-test` into
  `spring-boot-starter-webmvc-test` (package `org.springframework.boot.webmvc.test.autoconfigure`),
  the same split `@DataJpaTest` got. `RestTestClient` injection needs `spring-boot-resttestclient`
  + `@AutoConfigureRestTestClient`; inside a `@WebMvcTest` it's bound to MockMvc automatically.
  `@MockitoBean` (Spring Framework's replacement for Boot's removed `@MockBean`) swaps in the mock.
- **Keep the slice honest**: request/response DTOs (records), never entities, so the JSON is a
  deliberate contract. Pin the success shape once with `expectBody().json(..., JsonCompareMode.STRICT)`
  — strict mode fails on *extra* fields too, which is exactly how an accidental API change shows up.
  Use `jsonPath` for the remaining tests that only care about one or two fields.
- **One error contract**: have the `@RestControllerAdvice` return RFC 9457 `ProblemDetail` and
  extend `ResponseEntityExceptionHandler`, so framework-level failures (malformed JSON, `/orders/abc`
  type mismatch, missing `@RequestParam`, 415/406) get the same `application/problem+json` shape as
  your own domain exceptions. Gotcha: Spring omits `"type"` when it's the default `about:blank`.
- **What to `verify()` here**: the DTO → service-argument mapping is the controller's own logic, so
  an `ArgumentCaptor` on the service call is legitimate. For requests rejected before the handler
  runs (bad JSON, bad path variable, wrong verb/media type), `verifyNoInteractions(service)` proves
  the framework stopped them. Everything else is just `when(...)` stubbing.
- Build `Order` fixtures with an id via `ReflectionTestUtils.setField` rather than adding a
  test-only setter to the entity.

## 5. Full integration testing

- **Tools**: `@SpringBootTest(webEnvironment = WebEnvironment.RANDOM_PORT)` + Testcontainers for
  every external dependency in play (Postgres, Kafka, etc.), `RestTestClient` against the live
  server this time.
- Reach for this tier when you need to prove cross-cutting concerns actually work together: real
  Spring Security filter chain, real transaction boundaries, real serialization end-to-end. Keep
  this tier small — it's the slowest, and slices already cover most of the same ground faster.

## 6. Kafka producer/consumer testing

Three levels, in order of increasing realism:

1. **Unit**: call the `@KafkaListener`-annotated method directly with mocked collaborators. No
   Kafka involved at all — this is just testing the handler logic.
2. **Component**: Testcontainers Kafka module, a real broker. Produce a message onto the input
   topic, then assert the side effect (e.g. a row got written) using **Awaitility**
   (`await().untilAsserted(...)`) since consumption is asynchronous — never `Thread.sleep`.
3. **Producer side**: test the `KafkaTemplate` wrapper against the same Testcontainers broker by
   consuming from the topic in the test and asserting message shape, headers, and key.

Failure modes worth their own tests: retry/backoff behavior, dead-letter-topic routing, and
poison-pill handling (what happens when a message fails to deserialize).

## 7. Outbound REST calls to another service

- Unit-test the client wrapper's pure logic (URL building, request/response mapping, error
  translation) with mocks — no network involved.
- Component-test with **WireMock** standing in for the real endpoint: stub success, 4xx, 5xx,
  timeout, and slow-response scenarios. If using Resilience4j (retry/circuit breaker), assert that
  behavior explicitly against the stubbed failures.
- Optional, later: **Spring Cloud Contract** for consumer-driven contract tests, if the "other
  endpoint" is also something you own and can co-evolve the contract with.

## 8. Security testing

Layered, from cheapest to most realistic:

- **Method-security unit/slice tests**: `@WebMvcTest` + Spring Security Test
  (`SecurityMockMvcRequestPostProcessors`, or `RestTestClient`'s security support) —
  `@WithMockUser`, custom `UserDetails`, JWT post-processors. Assert 401 vs 403 vs 200 per role for
  every protected endpoint, and test `@PreAuthorize`/`@PostAuthorize` method rules directly.
- **CSRF testing** for any stateful (cookie/session) endpoints.
- **Full integration test with a real auth provider** (e.g. a Keycloak Testcontainer) for the one
  or two tests that need to prove the entire chain — token issuance through to authorized
  response — actually works end-to-end. Keep this to a minimum; it's expensive.

## 9. Edge cases & cross-cutting concerns

- Bean Validation edge cases: null, blank, boundary length/value, malformed input — and assert the
  exact `@ControllerAdvice` error contract each one produces.
- Time-dependent logic: inject `java.time.Clock` rather than calling `Instant.now()`/`LocalDate.now()`
  directly, so tests can fix the clock and be deterministic.
- Idempotency and concurrency edge cases where the domain has them (e.g. double-submit, race on a
  unique constraint).
- **Property-based testing with jqwik** for pure functions with large input spaces — optional,
  worth introducing once the example-based basics above are solid.

## 10. Architecture & suite-quality tests

- **ArchUnit**: encode layering rules as an actual test (e.g. "controllers must not depend on
  repositories directly") instead of leaving them as a code-review convention that erodes over
  time.
- **PIT mutation testing**: run periodically to check whether the suite actually *catches* bugs
  (by injecting small mutations into the code and seeing if any test fails), not just whether it
  hits high line coverage. High coverage with weak assertions is a common trap — this catches it.

## 11. Tooling setup notes (for when code starts)

Maven dependencies to bring in per topic, roughly in the order they'll be needed:
`spring-boot-starter-test` (JUnit 5, AssertJ, Mockito bundled), `testcontainers` +
`testcontainers-junit-jupiter` + the Postgres and Kafka Testcontainers modules, `wiremock`,
`awaitility`, `spring-security-test`, `archunit-junit5`, and later `jqwik` / `pitest-maven`.

Split test tiers with `@Tag("unit")` / `@Tag("integration")` and a Maven Surefire (unit, runs on
every build) + Failsafe (integration, runs as a separate, slower phase) split, so the fast loop
stays fast. Package-per-feature layout so each topic above has an obvious home once the source
tree exists.

## 12. Suggested build-up order

A literal checklist — implement one small, real feature slice per step, testing it with that
step's technique before moving on, rather than building contrived toy examples:

1. One entity + repository → repository tests (§3)
2. A service using that repository → unit tests with mocked repository (§2)
3. A controller exposing that service → `@WebMvcTest` slice tests (§4)
4. Wire it all together → one or two full integration tests (§5)
5. Add a Kafka consumer/producer around the same domain → all three Kafka test levels (§6)
6. Add an outbound call to a fake "other service" → WireMock-backed tests (§7)
7. Add security to the endpoints → layered security tests (§8)
8. Go back and fill in edge cases across everything built so far (§9)
9. Add ArchUnit rules and run PIT once there's a real suite to evaluate (§10)
